# Контракт доказательности inventory

Этот документ задаёт правила интерпретации inventory HomeRoute. Его задача — не позволить одному удачному запуску превратиться в необоснованное утверждение о совместимости или минимальных требованиях.

## Уровни утверждений

### VERIFIED

Факт непосредственно наблюдался на конкретной системе и может быть воспроизведён тем же read-only способом.

Примеры:

- архитектура CPU конкретного reference-router;
- объём RAM в момент inventory;
- наличие `/opt`;
- путь к конкретному бинарнику;
- работающий AWG2 container на конкретном VPS.

`VERIFIED` относится только к той системе и тому моменту времени, для которых есть evidence.

### OBSERVED

Значение получено один раз, но пока не использовалось как основание для общего требования или compatibility verdict.

Этот статус полезен для ресурсных значений: свободной RAM, свободного storage, количества пакетов и других величин, которые могут меняться между запусками.

### NOT VALIDATED

Значение отсутствует, не может быть безопасно получено или ещё не проверено воспроизводимым способом.

`NOT VALIDATED` нельзя заменять предположением.

### DEPRECATED

Объект ранее существовал в reference installation, но был сознательно удалён и не входит в Golden State.

Для HomeRoute v0.1 это, среди прочего, относится к старому `Wireguard0`/`nwg0`, table `4098`, mark `0xffffaab` и `WG443_TEST`.

## Что inventory доказывает

Inventory может доказать:

- фактическое состояние конкретного устройства;
- наличие или отсутствие требуемого компонента;
- размер доступного ресурса в момент измерения;
- совпадение безопасных параметров между двумя снимками.

Inventory сам по себе НЕ доказывает:

- минимальную RAM для всех устройств;
- максимальное число клиентов;
- совместимость другой модели;
- пригодность непроверенного KeeneticOS port;
- запас производительности под будущие функции.

## Правило числовых требований

Числовая граница `minimum` или `recommended` может появиться в документации только после того, как есть воспроизводимые данные, позволяющие объяснить её происхождение.

Для каждого будущего порога должны быть указаны:

1. какие reference inventories использованы;
2. какое фактическое потребление/ограничение наблюдалось;
3. какой safety margin выбран и почему;
4. какие сценарии проверялись;
5. какие ограничения остаются.

До этого момента используется `NOT VALIDATED`, а не приблизительное число.

## Правило compatibility matrix

- `Unknown` — данных нет.
- `Expected` — есть документированная техническая предпосылка, но HomeRoute целиком не проверялся.
- `Verified` — HomeRoute фактически воспроизведён на этой модели/конфигурации с сохранённым evidence.
- `Not suitable` — есть воспроизводимая причина несовместимости.

Похожая архитектура CPU или объём памяти сами по себе не дают статус `Verified`.

## Сравнение снимков

Нормализованные JSON-снимки можно сравнить:

```sh
python3 scripts/inventory/compare_inventory.py before.json after.json
```

Сравнение показывает изменение полей, но не оценивает изменение как хорошее или плохое. Интерпретация всегда должна учитывать контекст теста.

## Публичный репозиторий

В Git допускаются только значения из allowlist schema. Полный сырой лог preflight может использоваться для анализа в приватном рабочем контексте, но не должен автоматически коммититься.
