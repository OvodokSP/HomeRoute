# Backup / restore contract

Статус: **repository contract tested only on fictitious data**. Этот документ не разрешает backup/restore на реальном Keenetic или VPS без отдельной implementation/validation задачи.

## Цель

Любой будущий изменяющий installer должен уметь вернуть только объекты своей транзакции в состояние до apply. Rollback не должен быть «сбросом системы» и не должен удалять неизвестные пользовательские объекты.

## Transaction model

Перед первым изменением создаётся transaction id и manifest. Для каждого управляемого объекта manifest фиксирует одно из исходных состояний:

- `present` — объект существовал до apply, его исходная версия сохранена;
- `absent` — объекта не было до apply; rollback имеет право удалить только созданный этой транзакцией объект.

Объект, отсутствующий в manifest, rollback не трогает.

## Backup contract

Для существующего файла должны сохраняться:

- относительный идентификатор/путь объекта;
- исходное содержимое в приватном backup-каталоге;
- факт исходного существования;
- metadata, необходимые для корректного восстановления, когда implementation это поддерживает.

Backup:

- не хранится в Git;
- не печатает содержимое secret-файлов в stdout;
- создаётся до первого изменения соответствующего объекта;
- не считается успешным, если snapshot обязательного объекта не удалось получить.

## Restore contract

Rollback выполняется в обратном порядке применённых операций.

Для `present` объекта:

- восстановить snapshot;
- не заменять его guessed/default содержимым.

Для `absent` объекта:

- удалить его только если он был создан текущей транзакцией;
- не удалять одноимённый объект, если ownership текущей транзакции доказать нельзя.

## Isolation rules

Rollback не должен:

- удалять файлы, containers, firewall rules, routes или peers, которых нет в transaction manifest;
- восстанавливать весь `/opt`, `/etc`, Docker state или firewall wholesale;
- использовать backup другой транзакции без явного выбора;
- считать backup-архив частью публичного репозитория.

## Failure behavior

Если restore частично не удался:

- остановиться с FAIL;
- перечислить только идентификаторы невосстановленных объектов без secret contents;
- не продолжать разрушительные cleanup-действия вслепую.

## Fake-data acceptance test

`tests/backup-restore-contract.sh` проверяет контракт только в временном каталоге:

1. существующий managed-файл снимается в snapshot;
2. отсутствующий managed-файл фиксируется как `absent`;
3. unrelated-файл существует, но не входит в manifest;
4. имитируется apply: существующий файл меняется, отсутствующий создаётся;
5. restore возвращает существующий файл к snapshot;
6. созданный текущей транзакцией файл удаляется;
7. unrelated-файл остаётся неизменным.

Успешность этого теста доказывает только модель transaction isolation на фиктивных файлах. Она не доказывает готовность backup/restore для живого роутера/VPS.
